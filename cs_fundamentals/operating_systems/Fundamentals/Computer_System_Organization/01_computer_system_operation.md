# Computer System Operation

## Overview

A modern computer system consists of one or more CPUs, device controllers, and shared memory connected through a common bus. Understanding how these components work together is fundamental to grasping operating system concepts.

## Bootstrap Process

### Power-On Self-Test (POST)
When a computer powers on, the following sequence occurs:

1. **Firmware initialization** (BIOS/UEFI)
   - Stored in ROM/Flash
   - Initializes hardware components
   - Performs hardware diagnostics

2. **Bootloader execution**
   - Loads from boot device (disk, network, USB)
   - Small program that loads the OS kernel

3. **Kernel initialization**
   - OS kernel loaded into memory
   - Initializes system services
   - Starts first user process (init/systemd)

### Boot Sequence Example (x86 PC)

```
Power On
   ↓
BIOS/UEFI (ROM)
   ↓
POST (Hardware Check)
   ↓
Boot Device Selection
   ↓
Bootloader (GRUB/Windows Boot Manager)
   ↓
Kernel Load (Linux/Windows NT)
   ↓
Init Process (systemd/init.d)
   ↓
User Login
```

### Firmware Types

#### BIOS (Basic Input/Output System)
- Legacy firmware interface
- 16-bit mode initially
- Limited to MBR partition scheme (2TB disk limit)

#### UEFI (Unified Extensible Firmware Interface)
- Modern replacement for BIOS
- Supports GPT partitions (larger disks)
- Secure Boot capability
- Faster boot times

## Interrupt-Driven Operation

### What is an Interrupt?

An **interrupt** is a signal to the CPU that causes it to temporarily suspend current execution and transfer control to an **interrupt handler**.

### Types of Interrupts

#### 1. Hardware Interrupts
Generated by hardware devices:
- **I/O completion**: Disk read finished, network packet arrived
- **Timer**: Periodic clock interrupt
- **Error conditions**: Parity error, device failure

#### 2. Software Interrupts (Traps/Exceptions)
Generated by software:
- **System calls**: User program requests OS service
- **Exceptions**: Division by zero, page fault, illegal instruction

### Interrupt Handling Process

```
1. Device signals interrupt
   ↓
2. CPU finishes current instruction
   ↓
3. CPU saves current state (PC, registers)
   ↓
4. CPU loads Interrupt Service Routine (ISR) address
   ↓
5. ISR executes (handles interrupt)
   ↓
6. CPU restores saved state
   ↓
7. Resume interrupted program
```

### Interrupt Vector Table

The **Interrupt Vector Table (IVT)** maps interrupt numbers to handler addresses:

```
┌─────────┬──────────────────┐
│ IRQ #   │ Handler Address  │
├─────────┼──────────────────┤
│   0     │ 0x00001000       │  Timer
│   1     │ 0x00001100       │  Keyboard
│   2     │ 0x00001200       │  Cascade
│   3     │ 0x00001300       │  COM2
│   4     │ 0x00001400       │  COM1
│   ...   │ ...              │
└─────────┴──────────────────┘
```

### Example: Timer Interrupt

```c
// Pseudocode for timer interrupt handler
void timer_interrupt_handler() {
    // Save current process context
    save_context(current_process);

    // Update system time
    system_time++;

    // Check if time quantum expired
    if (current_process->time_slice == 0) {
        schedule_next_process();
    }

    // Restore context (possibly different process)
    restore_context(current_process);

    // Return to execution
    return_from_interrupt();
}
```

### Interrupt Priority

Not all interrupts are equally important. Systems use **priority levels**:

```
High Priority
    │
    ├─ Power Failure (must save state immediately)
    ├─ Machine Check (hardware error)
    ├─ Timer (critical for scheduling)
    ├─ Disk I/O
    ├─ Network
    ├─ Keyboard
    └─ Mouse
Low Priority
```

A higher-priority interrupt can **preempt** a lower-priority interrupt handler.

## I/O Operation Models

### 1. Programmed I/O (Polling)

CPU repeatedly checks device status:

```c
// Pseudocode
void read_data_polling() {
    while (!device_ready()) {
        // Busy wait (wastes CPU cycles)
    }
    data = read_from_device();
}
```

**Disadvantages**:
- CPU wastes cycles in busy-waiting
- Inefficient for slow devices

### 2. Interrupt-Driven I/O

Device signals CPU when ready:

```c
// Pseudocode
void initiate_io() {
    start_device_operation();
    // CPU continues with other work
}

void io_interrupt_handler() {
    data = read_from_device();
    process_data(data);
}
```

**Advantages**:
- CPU free to do other work
- Efficient for most I/O

**Disadvantages**:
- Interrupt overhead for each byte (high-frequency I/O)

### 3. Direct Memory Access (DMA)

Device transfers data directly to memory without CPU intervention:

```
CPU initiates DMA
   ↓
DMA controller takes over bus
   ↓
Device → DMA Controller → Memory (direct transfer)
   ↓
DMA completes, interrupts CPU
```

**Advantages**:
- CPU only interrupted once (not per byte)
- High-speed data transfer
- Efficient for bulk transfers

**Example Use Cases**:
- Disk I/O
- Network packet reception
- Graphics rendering

## Storage Hierarchy

### The Memory Pyramid

```
     Fast
      ↑
   Registers (CPU)          <1 ns      KB
   L1 Cache                 ~1 ns      KB
   L2 Cache                 ~4 ns      MB
   L3 Cache                 ~10 ns     MB
   Main Memory (DRAM)       ~100 ns    GB
   SSD                      ~100 µs    TB
   HDD                      ~10 ms     TB
      ↓
     Slow
```

### Caching Principle

Data is copied from slower to faster storage temporarily:

1. **CPU requests data**
2. **Check L1 cache** → Hit? Return data
3. **Check L2 cache** → Hit? Return data, copy to L1
4. **Check L3 cache** → Hit? Return data, copy to L2, L1
5. **Check main memory** → Fetch data, populate caches
6. **Check disk** → Load into memory, populate caches

### Cache Hit vs Cache Miss

```c
// Simplified cache lookup
int read_memory(address) {
    if (in_cache(address)) {
        return cache[address];  // Fast (cache hit)
    } else {
        data = fetch_from_memory(address);  // Slow (cache miss)
        cache[address] = data;  // Populate cache
        return data;
    }
}
```

## Dual-Mode and Multi-Mode Operation

### Why Dual-Mode?

To protect the OS from user programs and programs from each other:
- **User mode**: Limited privileges
- **Kernel mode**: Full privileges

### Mode Bit

A special **mode bit** in the CPU indicates current mode:
- `0` = Kernel mode
- `1` = User mode

```
┌─────────────────────────────┐
│  User Program               │
│  Mode = 1 (User)            │
│  Cannot execute privileged  │
│  instructions               │
└──────────┬──────────────────┘
           │ System Call
           ↓
┌─────────────────────────────┐
│  OS Kernel                  │
│  Mode = 0 (Kernel)          │
│  Can execute all            │
│  instructions               │
└──────────┬──────────────────┘
           │ Return
           ↓
┌─────────────────────────────┐
│  User Program (continues)   │
│  Mode = 1 (User)            │
└─────────────────────────────┘
```

### Privileged Instructions

Only executable in kernel mode:
- **I/O instructions**: Directly access devices
- **Memory management**: Modify page tables
- **Timer manipulation**: Prevent infinite loops
- **Interrupt control**: Enable/disable interrupts
- **Halt instruction**: Stop the CPU

**Example**:
```assembly
; x86 assembly
IN AL, 0x60    ; Read from keyboard port (privileged)
OUT 0x64, AL   ; Write to port (privileged)
CLI            ; Clear interrupts (privileged)
STI            ; Set interrupts (privileged)
HLT            ; Halt CPU (privileged)
```

Attempting these in user mode triggers a **trap** (exception), transferring control to the OS.

### Modern Multi-Mode Systems

x86 CPUs have **4 privilege rings**:

```
Ring 0 (Kernel)      ← Most privileged
Ring 1 (Device Drivers) ← Less commonly used
Ring 2 (Device Drivers) ← Less commonly used
Ring 3 (Applications)   ← Least privileged
```

Most OSes use only Ring 0 (kernel) and Ring 3 (user).

## Timer Mechanism

### Purpose

Prevent a process from monopolizing the CPU:
1. **Set timer** before switching to user mode
2. **Timer decrements** with each clock tick
3. **Timer expires** → Interrupt generated
4. **OS regains control**, can schedule another process

### Timer Implementation

```c
// Simplified timer mechanism
void start_timer(int milliseconds) {
    timer_value = milliseconds * TICKS_PER_MS;
    enable_timer_interrupt();
}

void timer_interrupt_handler() {
    timer_value--;

    if (timer_value == 0) {
        // Time quantum expired
        context_switch_to_scheduler();
    }
}
```

### Variable Timer

Modern systems use **variable timers** for flexibility:
- **Fixed-rate timer**: E.g., every 10ms
- **One-shot timer**: Single interrupt after delay
- **Periodic timer**: Repeated interrupts

## System Performance Considerations

### Context Switch Overhead

Switching between processes is expensive:
1. Save current process state
2. Update process control block
3. Switch memory mappings
4. Load new process state
5. Flush CPU caches (cache pollution)

**Typical cost**: 1-10 microseconds (thousands of cycles)

### Interrupt Overhead

Each interrupt has overhead:
1. Save registers
2. Determine interrupt source
3. Call handler
4. Restore registers

**Optimization**: Batch interrupts, use DMA for bulk transfers

## Key Takeaways

1. **Bootstrap**: Firmware → Bootloader → Kernel → Init
2. **Interrupts**: Hardware/software signals that divert CPU execution
3. **I/O Models**: Polling (inefficient), Interrupts (good), DMA (best for bulk)
4. **Dual-mode**: User mode (restricted) vs Kernel mode (privileged)
5. **Timer**: Prevents process monopolization, enables time-sharing
